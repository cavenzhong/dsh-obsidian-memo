# 给 DSH 的任务：实测一篇 Project 能不能跟着事实改变

请执行这份任务，不只写测试计划。你是验收员，不是项目文档的作者。使用 **DSH 中实际加载的 dsh-obsidian-memo 0.17.0 工作树版本、插件自己的新建/补充流程和一个已配置的真实模型**。本轮只验收，不修代码、不改提示词、不代替插件生成或润色结果。最后返回一个可供另一位评审独立复核的证据包。

## 1. 准备与边界

- 新建隔离的测试 profile / 测试配置和空 vault。vault 内只设 `便签/` 与 `项目/`；证据放在 vault **外**。不接管正在使用的仓库或覆盖个人设置。无法隔离就停止，报告缺什么。
- 核实运行的是本次**整稿修订版**，不能只看版本号：记录实际加载的插件位置/构建标识；核对模型能读完整项目但只交回最新概况、本次记录、验收摘要，旧历史和手记由 Host 保留。使用该版默认的三份项目提示词、`PROJECT` 字段和一个固定模型/预算，全程不换。不要输出密钥、Cookie 或私人配置。
- 优先通过真实面板操作。如果无法自动操作界面，但已有宿主授权的插件 RPC 可用，可通过同一 Host 执行；界面、拖放和浮窗外观必须标为「未测」，不能拿 RPC 结果冒充。两者都不可用则交回阻塞报告，不用 mock、单元测试、聊天里直接写 Markdown 或另编一个生成器代替。
- 正常流程只需 **6 次项目模型调用**（一次新建评估、一次建档、四次补充）。先用正常预算跑第一遍。遇到失败保留第一次的错误与文件状态，不反复重跑挑最好的一次。每次只给插件当前这一张便签，不把任务书、后续便签或验收标准当作模型输入。

## 2. 投入五张便签

逐张把下表正文原样写到 `便签/` 中的对应文件（UTF-8，无 frontmatter）。写完一张就执行下一节对应步骤，不预先投放后面的材料。表中的先后就是事件顺序，不用给故事编日期。

| 步骤 | 文件名 | 完整正文 |

| 01 | `策划碰头.md` | 河湾声音展想试做一轮馆内试听，范围是渡口、钟楼、船坞三段录音，用展厅终端播放，不做线上版。目前只是提案。先把三段都放到终端上试听，再决定能否排开放场次。 |

## 3. 按真实用户的顺序操作

1. **建档。** 将 01 拖到「到项目 → 新建项目」，等评估返回，把名称确认成 `河湾声音展`。保存评估结果、验收浮窗原文和落盘的项目全文，再点浮窗的「确认」完成验收。预期只有一个 `项目/河湾声音展-项目.md`。
2. **模拟一次用户编辑。** 在 01 验收后，只在这个测试项目文件末尾加以下独立手写节，保存一份 `01-baseline.md`。这是唯一允许直接编辑项目正文的步骤。之后不能替模型补标题、补引用、还原手记或修改历史。

   ```markdown
   ## 我的手记
   下轮讨论时，先问讲解员有没有听清“潮汐表”三个字。
   这是我的备忘，不是开放条件。标记：HB-27。
   ```

3. **推进、推翻、部分解决。** 依序把 02、03、04 拖入**同一个已有项目**。每次都等任务到待验收，先保存新项目全文、当次源便签和浮窗原文，**再点「确认」**开始下一次。不要重新建档。特别保留 03 和 04 两份完整稿，不能只留最终一份。
4. **恢复排期，再撤销。** 投入 05 前，按原始字节备份项目和 `签收回执.md`。补充后先取证（此时应能读到恢复排期的版本），这次**不要点「确认」，直接点「撤销」**。再保存两份文件，分别比较撤销前基线与撤销后的 SHA-256。预期项目精确恢复为 04 的已验收版本，05 便签精确恢复为没有 `PROJECT` 字段的原文。不要手工回滚，也不要为了让项目看起来成功而再次投 05。

**如果走 RPC：** 在已认证 `/sticky-notes` 上，01 用 `projectCheck` → 按 `jobId` 轮询 `state` → `openProject`（带 01 的绝对 `path`、`name: "河湾声音展"`、评估的 `job.result.sourceRevision` 作为 `sourceRevision`，及实际 `expectedProjectDir`）；后续用 `addProject`（源便签绝对 `path`、`filename: "河湾声音展-项目.md"`、同一 `expectedProjectDir`）。等本任务 `review: true` 并取出原始 `job.summary`，再 `acceptProject` 或 `undoProject`。RPC 返回 `jobId` 不等于写入成功。若出现终态错误，记录 `errorCode` / `error`、当时两个文件是否改变；依赖这一步的后续项目标「未测」。

## 4. 交回什么

在证据目录放好以下内容，然后压缩为 `Project-0.17-验收-<run-id>.zip`。无法打包时返回证据目录的**绝对路径**。即使失败也交回已有证据。

```text
REPORT.md                # 环境、执行方式、每步结果、异常与未测项
projects/                # 01.md、01-baseline.md、02.md、03.md、04.md、05-baseline.md、05-before-undo.md、05-after-undo.md
sources/before/          # 五张原始便签
sources/linked/          # 每步写入后、验收或撤销前的当次源便签；保留原文件名
sources/after-undo/      # 撤销后的签收回执.md
```

`REPORT.md` 请至少给两张表：

- **运行记录：** 步骤｜实际入口（UI/RPC）｜成功/失败/未测｜耗时｜**浮窗逐字原文或明确标识的 `job.summary`**｜操作（验收/撤销）｜对应快照。能截图时附 03、04 或 05 的真实浮窗截图；没看到就写没看到。报告最后列出 05 操作前和撤销后两对文件的四个 SHA-256，以及便签是否仍在原路径。
- **事实抽查：** 在 03、04、05 的顶部概况各摘一条改变判断的原句，抄出它实际使用的句内链接、对应便签名、支持判断的原文。没有句内链接、链接只在文末或实际指错文件，就照实记；不要补链。另外区分「链接文字就是支持判断的事实」和「链接在句内，但显示的仍只是文件名」；不按双链数量或字数打分。能在 Obsidian 实际点击则记录落点，否则只标「已核对文件与内容，未实点」。

## 5. 评审依据（不要喂给生成模型）

- **只读顶部是否够用？** 03 应取代“可排期”的旧现状；04 不能把 A 通过夸大成解除暂停，读者应知道还缺 B；05 应区分“恢复排期”和“已经开放”。三段馆内试听的范围没有变。不要因为措辞不同扣分，也不要把昨日的判断作为今日未解决的第二个结论。
- **有没有把证据用对？** 有价值的是从判断点回支持该判断的便签，不是双链总数。04 的证据不能提前证明 B 通过，05 也不能证明已经开场。摘要应说清变化；04 最能测出模型是否只会说“项目已更新”。
- **哪些是硬底线？** 从 02 起，每个修订都应保留旧历史原文与顺序，只在底部增加当次记录；手记不得改写或被当作开放条件；源便签不移动、指向同一项目；双文件撤销必须精确还原。一次失败被安全拒写，应分别记为“这次更新失败”和“文件得到保护”，不要合并成通过。

结束时不要只回「已完成」。请返回 **证据包路径、实际模型、成功走到哪一步、最值得评审看的一个现象**。不要删除证据包。
